# RFC: サブエージェントのVM実行と容量管理

状態: **Draft / 設計提案。VM実行機能を実装・公開したPRではない。**

調査日: 2026-10-23。基準は本リポジトリ main `28d1f62818c42a9c6cb64af361c93157e2926827`、DSH `0.2.1-rc.2`、Lima `2.2.1`。並行開発中のPR #13 / #14を変更せず、実装時に取り込み後のコードへ合わせる。

実際に導入したDSH、ブラウザ確認、Lima CLIの検証結果と、読んだソースへの固定参照は [検証記録](vm-execution-validation.md) に分ける。以下の設定名・API・初期値は提案であり、既存機能ではない。

## 1. 何を実現するか

対象は **サブエージェントだけをVMへ送る方式**。親のDSH、UI、既存ホストプラグインは移さない。

代表例は「親はホストRead-onlyで調査・計画し、workerだけがVM内で実装・テストする」。VMには作業開始時のワークスペースのコピーを渡し、終了後に回答と変更を回収する。ホストへの変更反映はユーザーの別操作であり、委任しただけでは発生しない。

同じ仕組みで、独立した並列修正、依存関係を変える実験、CLIバージョン別の検証、限定したツールでの調査を扱う。ロールのモデルや指示と、実行場所は直交する。

### 最初に固定する判断

| 項目 | 採用案 |
| --- | --- |
| VMバックエンド | Lima一種類から始める。独自VMM・汎用バックエンド登録基盤は作らない |
| 実行単位 | 1ジョブが1VMを専有。別ジョブとの同居はしない |
| 標準ファイル方式 | 明示的なコピー → 実行 → 私有領域への成果物回収 → ユーザーによる反映 |
| VM再利用 | 停止済みの環境テンプレートを再利用。タスクで変更されたVMはクリーンなテンプレートとして再利用しない |
| 容量 | VM数の上限・起動前予約・最低空き容量・所有物だけのGCを同時に実装 |
| 保存先 | まず一つの管理ルートを選ぶ。SSDでもHDDでもよい。自動SSD/HDD階層化は作らない |
| CLI | VM内のネイティブCLIを起動。既存descriptor / plan / parserを再利用 |
| DSH内蔵型 | 公式SDKをVM内で利用する専用経路。ホストのDSH全体やCordis contextはコピーしない |
| ホストツール | 初版ではVMへ自動公開しない。将来のツール橋渡しは別機能 |
| 無効・故障時 | 明示的なエラー。VM設定のロールを勝手にホスト実行へ落とさない |

「何でもできるVM管理製品」を作らず、委任に必要な作成・起動・コピー・実行・停止・削除を管理する。

## 2. コードを読んで修正した前提

### 2.1 Limaの `shell --sync` は採用しない

Lima 2.2.1の `cmd/limactl/shell.go` は、`askUserForRsyncBack` 内で `!tty` なら確認なしに `rsyncBack()` を呼ぶ。対話時の確認画面があることと、非対話実行で承認待ちになることは同じではない。

DSHがCLIのstdin/stdoutを使う経路に `limactl shell --sync` を組み込むと、ホストRead-onlyの親が委任した処理からホストへの書き戻しが発生し得る。したがって同期の便利コマンドを実行境界として使わない。これは以前の構想からの重要な修正。

### 2.2 既存エンジンは単にspawn先を変えれば動く構造ではない

`src/host/external/engine.ts` はspawn前にもホストの `node:fs` でcwdを調べ、ワークスペースを検査し、一時ファイルを作り、HOMEを解決し、実行ファイル・preflightを確認する。`${RUN_DIR}`、`${HOME}`、一部CLIのhousekeepingも実行先に依存する。

ホスト側の `ctx.subprocess` をLimaに差し替えるだけでは、Macの実行ファイルやホストの一時パスをLinuxゲストへ渡してしまう。実行先ごとの準備とプロセス所有を分離し、パーサーや結果変換だけを共有する。

### 2.3 DSH SDKは既にあるが、任意のリモートspawn APIではない

DSH rc.2には公式 `subagent-dsh-sdk` がある。別プロセスに独立したDSH runtimeを立て、公式SDKで駆動する仕組みは再利用できる。一方、SDKの `dshBin` はローカルNodeモジュールの指定であり、LimaやSSHコマンドに置換する契約ではない。SDK内部のfactoryをmonkey-patchしない。

DSHをゲストで動かす場合、SDKとその起動対象を**ゲスト側に置く**。ホストのAgentやSessionオブジェクトはシリアライズしない。

### 2.4 Lima cloneは常に小さな差分ディスクではない

Limaの `CloneOrRename` は稼働中のVMを複製できず、ファイルコピーでCoWを試みる。CoWが使えるかはファイルシステム等に依存する。HDDへ置けば必ずフルコピーになるとも、常に省容量になるとも断定しない。

容量の正しさをCoWに依存させず、上限と予約で守る。CoWは利用できたときの最適化とする。

### 2.5 LIMA_HOMEとダウンロードキャッシュは別

インスタンスは `LIMA_HOME` にあるが、Limaのダウンロードキャッシュは `os.UserCacheDir()/lima`。`limactl prune` は主としてそのダウンロードキャッシュを整理するコマンドであり、ジョブVMの回収ではない。

DSH専用LIMA_HOMEを作っただけで、共有ダウンロードキャッシュまでDSH所有になるわけではない。自動GCに裸の `limactl prune`、`delete --all`、ユーザーの `~/.lima` 再帰削除を使わない。

## 3. 利用者から見た設定と操作

グローバルにはVM実行のオン/オフ、保存先、使用上限、最低空き容量、同時実行数、自動整理を置く。ロールには既存のエージェント選択とは別に「実行環境: ホスト / VM」「VM環境」「ゲスト側の権限・ツールモード」を置く。

```yaml
# 設計例。現在のプラグイン設定としては使えない。
vm:
  enabled: false
  root: /Volumes/WorkHDD/dv
  maxBytes: 107374182400       # 100 GiB、セットアップ時に実ディスクで検査
  minFreeBytes: 21474836480   # 20 GiB、提案値
  maxConcurrent: 2
  maxJobInstances: 2         # 準備中・停止中・回収失敗も枠を消費
  autoCleanup: true

roles:
  - id: worker
    execution:
      target: vm
      environment: linux-dev
    # runner/model/instructions等は既存の責務を維持
```

VMオフはデータ削除ではない。新しいVMジョブを受け付けなくし、実行中は開始時に確定した設定で完走させる。「全実行を停止」は別操作にする。保存先を変更しても稼働中ジョブのパスを差し替えない。

ロールにVMが指定されているのにVM機能がオフ・ドライブ未接続・認証未準備なら、理由と回復操作を表示する。ロール定義を消さず、ホストへ自動フォールバックもしない。

VM管理画面はまず既存プラグイン設定の一セクションでよい。実行中一覧、結果待ち一覧、容量内訳、停止・成果物を見る・確認済みデータの掃除を扱う。独立した仮想化ダッシュボードや新しい全画面管理アプリは作らない。#13のロール表示に、実行場所と状態を足す場合も同じ台帳を読む。

## 4. 権限: ホストとゲストを混ぜない

現在の `readonly.ts` は `delegate` 先の `role.readOnly` がfalseなら拒否し、`tool.ts` は外部ランナーへ渡す前にこのチェックを行う。さらに `external/policy.ts` が親の権限上限へCLIプリセットを制限する。後段だけVM対応しても、最初のguardで止まる。

VM追加では「Read-onlyの例外を全部許す」のではなく、利用者が登録した環境に対する**隔離された作業の委任許可**を別に扱う。

| 親/操作 | 期待 |
| --- | --- |
| ホストRO → ホストの書き込みworker | 従来どおり拒否 |
| ホストRO → ユーザーが許可済みのVM worker | ホスト書き戻しなしで許可 |
| ホストRO → VMの差分をホストへ自動反映 | 拒否 |
| VM設定・保存先・共有・資格情報の追加をモデルが要求 | 設定権限なし。ユーザー操作が必要 |
| VM実行不可 → ホストで同じタスクを再実行 | しない |

この委任許可は、プラグインの私有領域への一時ファイル作成・VM管理を含む。親のユーザーワークスペースを編集する許可とは区別する。親の `sandbox/mode` をFull accessへ変更したり、ダミーの親Agentを作ったりしない。

実行直前に、設定済み環境、コピー元の読取許可、VM所有権、共有なし、容量予約を確認する。モデルの引数でVM名・任意YAML・保存先・ホストマウントを自由指定させない。ゲスト内のCLI権限は、親のホスト権限ではなく、利用者がその環境に許可したゲストの上限とロール設定から決める。ホスト実行の既存チェックはそのまま残す。

### 保証範囲

VMがあるだけで外部サービスへの変更までRead-onlyになるわけではない。コピーされた秘密情報、渡したAPIキー、リモートMCP、ネットワーク上のサービスは別の操作能力を持つ。

初版は「ホストの作業ファイルへ直接書き込まない」を明確な契約とし、資格情報とネットワーク利用は環境セットアップで明示する。マウント・agent forwarding・自動port forwardingの無効化は、外向き通信遮断と同義ではない。ホストの管理APIをゲストへ公開せず、DSHプロセスの認証URL/tokenや環境全体を転送しない。ホストROの親からの委任を許すのは、この別権限をユーザーが許可した環境に限る。

## 5. 実行の構造

```text
delegate(role, task)
  ├─ host: 現在のDSH/外部CLI経路を維持
  └─ vm: trusted role + environmentを解決
       → 容量/同時実行枠を予約
       → 停止した環境テンプレートを複製・起動
       → workspaceのコピーを配置
       → CLI または guest DSH SDKを起動
       → 結果と変更を私有stagingへ回収
       → VM停止を確認・削除
       → 既存SubagentRuntimeから親へ完了通知

ユーザーの「変更を適用」
  → 別のホスト側処理でbaseline検査
  → 競合表示または明示した変更だけ反映
```

既存 `external/provider.ts` とDSH公式 `SubagentProvider` / `startActivation` を使う。実行履歴、interrupt、親への結果通知を別の独自タスクシステムで二重実装しない。

初版のVM子は外部実行として扱い、fresh・one-shotとする。ローカルSessionがないのに `send_message` やforkを提供したと偽らない。必要なタスク情報を明示的に渡す。DSHの既存委任深度制限も維持し、ゲストで再帰委任を無制限に再開しない。

### 実行先依存の処理だけを分離

ホストとVMの二つの具体実装を置く。汎用ファイルシステムSDKや仮想化プラグインAPIを公開する必要はない。

- ホスト準備: 今のcwd検査、実行ファイル解決、一時ファイル、env、preflight、housekeeping。
- VM準備: ゲストのcwd/HOME/実行ファイル、一時ファイル、ゲストでのpreflight。ホストのPATHや絶対パスを転用しない。
- 共通: CLI plan生成、stdoutの行処理、CLI固有parser、最終回答・失敗分類。
- VM固有の所有: VMインスタンス、転送物、容量予約、結果回収、ゲストプロセスを含む停止。

`ctx.subprocess` 自体はグローバルに上書きしない。ホスト上で動く他のプラグインが突然VMへ送られることを避ける。追加する境界はこのプラグインの外部実行の内側だけにする。

### Guest launcher

Limaが用意するSSH経路を利用し、ジョブごとに起動して終了する小さなlauncherで十分。常駐guest HTTPサーバー、独自の認証サービス、別のエージェントハーネスは作らない。

launcherは固定されたguest側の私有specを読み、指定CLIをargv配列で起動する。タスク・秘密値をshell文字列へ連結せず、秘密をコマンドラインへ入れない。CLIのstdin/stdoutは既存プロトコルのまま流し、起動ログは混ぜない。特にPi RPCやOpenCode ACPには双方向stdinとキャンセル伝達が必要で、`ssh command < task.txt` の一発実行だけでは足りない。

SSH/Lima呼び出しが成功したことと、CLIが成功したことを分ける。SSH切断、CLI exit、プロトコル終端、回収失敗はそれぞれ区別する。

## 6. CLIとDSH内蔵子の扱い

### 外部CLI

VM側へLinux/CPUアーキテクチャに対応したCLIを用意する。ホストのMac用バイナリや `.venv` / `node_modules` をそのまま実行環境として流用しない。

既存CLIのネイティブ設定・拡張はゲスト環境で尊重する。Grok/Piのnativeを選ぶ場合、ホストFull accessを要求するのではなく、ユーザーが許可したVM内の実行権限で評価する。ただしVMを選んだだけで、ユーザーのCLIプリセットを勝手にbypassへ変更しない。

CLIのバージョン・検出パス・認証の診断も、ホストとVMで分ける。「ホストで見つかったからVMでも使える」としない。#14の互換性記録を拡張する場合も、実行場所・ゲストOS/arch・CLI版を記録するだけで、巨大な別認証制度は作らない。

### 認証と設定の永続性

実行環境と資格情報の寿命は同じではない。毎回ログインし直すUXは避けたいが、認証済みディスクを複製すれば必ず安全に継続利用できるとも限らない。refresh tokenの更新・同時使用・OS keychain依存をCLIごとに確認する必要がある。

最初に動作を保証する方式は、利用者が明示した環境変数名から必要な資格情報だけをジョブへ渡す方法とする。値は設定JSONやログに保存しない。APIキーがゲストから見える方式では、そのキーがゲスト権限の一部であると明示する。

OAuth等はguest環境のセットアップ画面で別途認証できる設計を残すが、未確認のCLIまで「一度のログインで全並列cloneに対応」と表示しない。認証状態を永続化する経路には、検証済みの対象ファイルだけを扱う方法、または専用環境を排他利用する方法の確認が必要。**タスク実行後のHOMEや仮想ディスクを丸ごとテンプレートへ戻す処理は作らない。** 本PRの次の実機検証で方式を確定するrelease gateとする。

ベース環境をタスクから更新しない。CLI・SDK・依存ツールの更新は、ユーザーによる環境メンテナンスで新revisionを作り、起動前に採用する。実行中の環境にグローバルupdateをかけない。認証領域をキャッシュ扱いで削除しない。

### DSHをVM内で動かす

CLIだけで要件完了とはしない。DSHロールのVM経路は、guestにインストールした同版のSDKがguestのDSH profileを起動する構成にする。結果は外部SubagentRunへ戻す。

guest profileは、必要なモデルprovider・ツール・プラグインを明示的に構成する。ホストの全プラグイン設定、ブラウザUI、秘密、Session履歴は自動複製しない。プラグイン独自のホスト操作やMac専用機能までVMへ移る保証はしない。

実装順はCLIで一本の経路を通してからDSH SDK経路へ進む。SDKの起動・モデル設定・失敗・停止は公式実装を利用し、似たLLMループを再実装しない。初回版ではfreshのみ。fork・追加メッセージ・親と同じPresetの完全再現は、上流の対応契約を確認してから別途扱う。

## 7. ツール限定モード

「モデルに見せるツール」と「コードが実際にできること」を同じラベルにしない。

DSH guestでは、ツール登録レイヤーの制限と実行時guardを利用する。プロンプトに禁止事項を書くだけにせず、後から登録されたツールにも同じ許可集合を適用する。guestに含めたプラグイン自体は信頼して実行するコードであり、ツールを隠すだけでその初期化処理を隔離したことにはならない。

外部CLIでは、そのCLIが提供する機能を利用する。Piの `--tools` を指定しても任意の拡張の初期化コードまで制限したことにはならない。未対応のツール指定を無視して「制限済み」と表示しない。まず「Native」と実際に検証できた「Selected tools」を区別し、対応しない組み合わせは保存時・起動時に説明する。

VM内で自由に編集できるworkerモードと、VM内のワークスペースも変更しないreviewモードは別。後者はゲストFS権限/CLI機構等の実機検証後に提供する。ROの名前だけを付けて実際には書ける状態にしない。

ホストのMCPや他プラグインをVMへRPCで公開するgatewayは初版に含めない。後で必要になったとき、指定ツールだけの追加能力として設計する。VM環境でhostの `plugin_manager` や任意ホストコマンドが使える抜け道を作らない。

## 8. ワークスペースと変更反映

### コピー元

コピー元は親が読める、利用者の指定したワークスペース内に限定する。未コミット・未追跡ファイルを含む**現在の作業状態**が必要であり、単なる `git clone HEAD` ではない。Gitを使っていないディレクトリにも対応する。

既定除外はVCS制御データ、再生成可能な大きな依存/ビルド領域、明示した秘密ファイルとする。除外一覧・概算容量・理由をセットアップで見せ、ユーザーが必要なファイルを追加できるようにする。`.env.example` のようなテンプレートまで無言で除外しない。ファイル名だけで秘密を完全検出できるとは主張しない。

ホストの `.git` をそのまま渡さず、必要ならguestに独立した作業用Git metadataを作る。ホストのhook、credential helper、worktreeの絶対参照を実行しない。コピーから漏れた変更や未対応ファイルは結果で明示する。

コピー中のファイル変更を検知したら、そのファイルを読み直すかジョブをやり直す。初版でディスク全体の原子的snapshotを実装する必要はないが、不整合な入力を「同一時点」と偽らない。

外向きsymlinkを辿ってホストの別ディレクトリを収集しない。socket/device/FIFOを転送しない。host側の実行パスではなくguest側の `/workspace` 等へ配置する。スペース・日本語・バイナリファイルを受入テストに含める。

### 成果物

開始時baselineをホスト私有領域で保持する。guestから返ったbaselineを信用して上書き判定しない。結果には変更ファイルの内容とhash、追加・削除・mode変更、CLIの要約・診断、入力除外の情報を含める。

成果物はホストの元workspaceではなく、管理ルートのstagingへ受信する。ファイル数・展開後サイズ・合計サイズを制限し、絶対パス、`..`、重複/衝突パス、外向きリンク等を拒否する。guestが返した任意tarをホストworkspaceへ直接展開しない。

初版では通常ファイル・ディレクトリ・実行bitを中心に扱い、symlinkの追加/変更など未対応の反映は明示的に拒否する。既存symlinkを辿る上書きはしない。VM本体を残す代わりに、確認が必要な成果物だけを保持する。

### 反映

ホストへ反映する操作はユーザー向けの別RPC/UI。親のRead-onlyを迂回して呼べるモデルツールとして登録しない。

対象ごとに開始時hashと現在のホストを比較し、同一ファイルを別ワーカーやユーザーが変更していれば競合とする。自動上書き・自動マージはしない。guestでの削除も同じ前提を要求する。

初版はファイル単位の選択でよく、行単位の高度なmerge editorは不要。適用直前に再検査し、workspace単位で直列化する。複数ファイルの変更を完全なFS transactionと呼ばない。途中失敗は適用済み一覧と退避データを残し、成功扱いにしない。ローカルの同時編集に対する限界も表示する。

## 9. 停止・クラッシュ・並列実行

状態は次の程度に抑える。詳細なイベントログ全体を別DBへ二重保存しない。

```text
queued → preparing → running → collecting → stopping → finished
                ↘ interrupted / failed / cleanup-required
```

runごとにVM名・environment revision・workspace ID・容量予約・成果物・状態を既存 `storageDomain` に保存する。削除対象の所有markerは管理ルートにも持ち、台帳が壊れたとき未所有ファイルを推測で削除しない。ゲストから送られたVM名やパスをGC対象として採用しない。

キャンセルはCLI固有のgraceful cancelを試し、期限後はそのジョブのVMを停止する。ホストのSSHプロセス終了だけではguestの子孫終了を証明できない。1ジョブ1VMなら、VM停止確認を最終的な終了境界にできる。他ジョブを巻き込む停止はしない。

正常終了も回収後にVMを止め、必要な成果物の保存とVM停止を確認してからDSHへ完了を返す。stop/deleteに失敗したVMは `cleanup-required` として容量・個数枠を保持する。ログ上だけ「解放済み」にしない。

ホストクラッシュ後は、自動再実行せず台帳と実VM状態を照合する。古いPID/TTLだけで停止済みと判断しない。ホストが落ちている間の停止保証は別問題であり、guest側の期限処理も検証する。期限処理がroot権限を持つguestから改変可能な構成では、それを強い隔離保証と呼ばない。未確認ジョブを次回起動時に回収できることを最低条件とする。

グローバル停止・アンロード・timeout・ユーザーinterruptは同じcleanup入口へ合流し、二重停止/二重予約解放を防ぐ。

## 10. HDD/SSDとストレージ管理

### 10.1 保存先はまず一つ

初版の設定は短い絶対パスの管理ルート一つにする。例は `/Volumes/WorkHDD/dv` や `/mnt/hdd/dv`。この下に専用Lima home、input/output staging、環境manifest、私有download cacheを置く。小さい状態台帳は既存DSH storageDomainを使う。

HDD上でも利用できるようにするが、単に「HDD」という名前だけで判断しない。実ファイルシステム、socket、sparse file、atomic rename、空き容量、権限をpreflightする。低速時は性能上の注意を出す。ベンチマークしていない速度や節約量を表示しない。

Limaはパスを実体へ解決し、macOSではUnix socketの長さ制約もある。長い保存先に短いsymlinkを付ければ解決するとは限らない。実パスを使って検査し、未対応の保存先は起動前に説明する。

自動hot/cold移動、SSD上の実行ディスクとHDD上の全種類キャッシュの個別階層化、分散ストレージは作らない。必要になれば後で「VM root」と「成果物/ダウンロードroot」の二つへ分けられるが、初版から多階層設定を持たない。

### 10.2 管理するもの/しないもの

| 種類 | 寿命と削除 |
| --- | --- |
| 環境テンプレート | revision固定。参照中・保護済み・認証を含むものは自動削除しない |
| ジョブVM | 同時数を制限。成果物回収と停止後に削除 |
| 入力snapshot | 結果反映のbaselineに必要な期間だけ保持 |
| 未確認成果物 | VMと独立して保持。既定で無断削除しないが、上限に達したら新規実行を止める |
| 確認済み/破棄指定成果物 | TTLと容量圧迫時のGC対象 |
| 私有download cache | 未参照をLRU/TTLで削除可能 |
| npm/pip cache | 初版はguestディスクの一部として計上。共有RWキャッシュサーバーは作らない |
| ログ | runごとの上限と世代管理。秘密値や巨大stdoutを無制限に保存しない |
| ユーザー認証・環境設定 | キャッシュではない。削除は別の明示操作 |
| ユーザーの既存Lima VM/共有cache | 管理対象外。勝手に掃除しない |

Lima cacheをDSH専用rootへ確実に向けられないOSでは、共有cacheを使用量と区別して表示し、自動削除対象にしない。大きなimage downloadはDSH所有ディレクトリにdigestを検証して保存し、ローカルファイルとしてLimaへ渡す方式を優先検証する。Limaのローカルファイル利用ではdigest検証が省略され得るため、DSH側で検証したという根拠を必要とする。初版から全テンプレートの任意URL書換え機構は作らず、管理する既知のimage/provision recipeに限定する。

### 10.3 容量は観測値と予約の両方で管理

仮想ディスクの最大サイズ、ホストに実際に割り当てた容量、CoW共有、削除で回収できる容量は同じではない。UIでは「実使用量（推定/測定方式）」「実行用に予約した残り」「保護データ」「外部管理cache」を区別する。

起動前に、少なくとも次を同じロック下で判定・予約する。

```text
現在の管理使用量
 + 既存ジョブがまだ増やせる予約残量
 + 今回の最大増分（clone/ディスク上限/転送/成果物/ログ）
 <= 設定された管理上限

実ボリュームの空き容量
 - 全ジョブの予約残量
 - 今回の最大増分
 >= 最低空き容量
```

既に割り当て済みのジョブ容量を使用量と予約で二重計上しない。別rootが同じ物理/論理ボリューム上なら空き容量を二重に見積もらない。CoWの共有量を正確に得られない場合は、楽観的な割引をせず保守的に予約する。

容量が足りない場合、削除可能なデータを整理し、足りなければキュー/停止理由を表示する。容量不足から抜けるために未確認成果物や認証を消さない。

これはファイルシステムのhard quotaそのものではない。他アプリの書き込み、計測誤差、backendの一時領域まで絶対に上限内と保証しない。定期/節目の空き容量検査と、受信サイズ上限、低空き時の新規受付停止を組み合わせる。hard quotaが必要な配備は対応FS側の設定を別途行う。

### 10.4 個数・予約を一つの管理主体が所有

まず一つのpoolを一つのDSHプロセスが排他所有する。同一poolを別profile/processが同時管理しようとしたら明示的に拒否する。分散ロックサービスや新DBは不要。プロセス内では予約とGCを一つのqueueで直列化し、永続化が終わる前に次の予約を通さない。

`maxJobInstances` はrunningだけでなくpreparing、stopping、cleanup-requiredを含む。テンプレート作成と更新も容量予約が必要。未確認成果物の総量/件数も制限する。「VMだけ有限、結果は無限」にしない。

### 10.5 GC

節目（起動前、完了後、DSH再起動時）と低頻度のタイマーで、所有marker・台帳・利用中のleaseを照合して掃除する。各ファイルの細かなwatcherは不要。

削除順は、所有が確認できる未使用の一時データ、期限切れの確認済み成果物/ログ、未参照download、不要な古い環境revision。稼働中のVMや停止確認不能のVM、参照中のbase、未確認結果、認証は除外する。

ファイル名のprefix一致だけでは所有判定しない。削除前に親ディレクトリ/marker/volumeを確認し、他のジョブや任意ホストパスへのリンクを辿らない。VMは個別名を指定してLimaへ削除させる。ディスクの回収結果を再測定し、期待値だけ差し引かない。

未確認成果物を自動期限切れにする設定は、既定オフの明示的なデータ破棄ポリシーとしてのみ提供する。保護したデータで上限に達した場合は、何を確認/削除すれば再開できるか表示する。

### 10.6 外付けドライブと移行

セットアップでvolume identityとpool markerを記録する。ドライブが外れたとき、同名の空mount pointにディレクトリを作って内蔵SSDへ書き始めない。ボリューム不一致は起動/GC/反映を止める。

保存先変更は「全ジョブ停止 → 移行先の空き/対応FS確認 → コピーと検証 → 設定切替」の保守操作。ソース削除は検証後の別確認とする。ライブ移行やタスク中の自動退避は初版の対象外。

### 初期値の考え方

100 GiB、最低空き20 GiB、並列2は説明用の初期候補であり、固定要件ではない。小さいディスクではセットアップで調整する。ジョブディスク、転送、成果物の上限を合わせて二つ起動できるかを事前に表示する。CLIや依存環境で必要量は異なるため、「VMは常に20 GB」等の前提を埋め込まない。

## 11. 変更を局所化する実装順

1. **設定・台帳・容量予約**: VM既定オフ。environment/roleを検証し、専用rootの所有と容量管理を作る。この時点ではVM機能を提供したと表示しない。
2. **一本の外部CLI経路**: Lima clone/start、コピー、CLI起動、interrupt/timeout、成果物回収、stop/deleteを端から通す。ホストROの親はここで実E2Eする。
3. **既存CLIへ展開**: descriptor/plan/parserを再利用し、各CLIの認証・プロトコル・ゲストパスを実バイナリで確認する。ホスト経路を退行させない。
4. **結果確認とストレージUI**: 差分適用、競合、容量不足、外付け未接続、GCの説明を既存UIに載せる。
5. **DSH SDK guest / Selected tools**: guest profileの構成とツール制限を実DSHで確認する。CLI経路と同じVM/容量/成果物の管理を使う。

想定する追加モジュールは `host/vm/{manager,lima,workspace,storage}.ts` 程度から始め、必要なguest launcher一つを追加する。設定型はshared、UIは既存RolesPage/RoleEditorへ足す。ファイル数を先に増やすための空interfaceやレイヤーは作らない。

既存変更点は `readonly.ts` の委任判定、`tool.ts` の実行先分岐、`external/engine.ts` の実行先依存準備、状態保存と設定UI。PR #14で変わるCLI権限と競合しやすいため、この設計PRでは実装変更を混ぜない。既存バージョン向けmigration・二重設定・別ランタイムの複製は追加しない。

## 12. 不採用にするもの

| 案 | 今は採らない理由 |
| --- | --- |
| 親DSH全体をVMへ移す | 今回は子だけ。プラグインやUI全体の移転は別プロジェクト |
| limactl shell --sync | 非TTYで自動書き戻し。標準の承認フローと合わない |
| ホストworkspaceのRW共有 | ホストRO + guest編集の目的を壊す |
| 使用済みVMをworkspace削除だけで別タスクへ再利用 | OS/HOME/起動コードの変更が残る。クリーン環境とは言えない |
| CoWを前提とする容量計算 | 保存先FSにより複製コストが変わる |
| 最初からFirecracker/libkrun/Limaを抽象化 | backend管理と検証範囲が増える。まずLimaで成立させる |
| 既存SDKのローカルspawnをmonkey-patch | 公開契約ではなく、停止やパス解決を壊しやすい |
| DSHのfs/subprocessサービスを全体でSSH版に置換 | ホストの全プラグインへ影響する。ネイティブCLI全体をVMに置く要件とも別 |
| 任意ホストツールgateway | 権限設計が別途必要。初版のVM実行を重くする |
| 独自CAS/ブロック重複排除/自動SSD-HDD階層化 | backend/FSの機能と重複。容量上限・所有・GCを先に確実にする |

## 13. リリース前に満たす条件

このRFCは次の条件をすべて検証済みと主張しない。特に実VMの起動・隔離・cleanupは今回の環境では未検証。

- [ ] macOS/Apple SiliconとLinux/KVMで、管理したVMのboot/clone/stop/deleteが成立する。
- [ ] ホストRO親 → VM内worker編集 → host原本不変 → ユーザーの適用でのみ変更、を実DSHで確認する。
- [ ] dirty/untracked、日本語/空白パス、非Git、追加/削除/バイナリ、競合を扱える。
- [ ] CLI失敗・timeout・interrupt・通信断・アンロードでも、別ジョブを止めず子孫を回収する。
- [ ] 一つのジョブで不正な成功終端が出ても、回収/停止未完了を完了としない。
- [ ] CoWあり/なし、低空き、並列予約、ディスク満杯、GC競合、停止失敗を確認する。
- [ ] 未確認成果物で上限に達したら受付を止め、成果物/認証を無断削除しない。
- [ ] ドライブ抜去・同名mount point・長いsocket path・不対応FSで別の場所へ保存しない。
- [ ] 多数回の実行後もVM数・使用容量が設定内に戻り、未所有のLima VM/cacheに触れない。
- [ ] SDK guest、ツールallowlist、後からのツール登録、未対応CLI設定を実機で確認する。
- [ ] 各CLIの認証方法・更新/再ログイン・並列性の対応範囲を明示する。
- [ ] VMオフ時は通常ロールとホストCLIが従来どおり動く。VMロールは無断でホスト実行されない。

実装の判断基準は、独自機構の数ではなく、**既存のDSH/CLIを保ったまま、ホストへの影響・成果物・停止・容量の所有者が一意になること**とする。
